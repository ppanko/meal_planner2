# Supabase setup: household-code device enrollment

This version does **not** use email, Magic Links, OTPs, or passwords.

Each browser/device enters one household access code once. Supabase creates an
anonymous authenticated user for that browser and RLS authorizes the user ID
after the server validates the household code.

## 1. Update the database authorization layer

Open **Supabase -> SQL Editor** and run:

`supabase/setup.sql`

Run the whole file.

It preserves the existing `meal_planner_state` table/data.

The setup also installs version-checked writes and a rolling history of the 50
most recent confirmed states. Existing state begins at revision `0`; the next
successful application save advances it normally.

> Deploy the matching application build immediately after running this SQL.
> The migration disables legacy direct browser writes so older builds cannot
> bypass conflict protection.

### Save the generated household code

The first time the script creates the access-code record, the SQL result contains:

```text
household_access_code
------------------------
<random 24-character code>
```

Save that value somewhere private.

The database stores only its SHA-256 hash. If the SQL has already been run once,
re-running it does not replace the code and therefore returns no new code.

## 2. Enable anonymous sign-ins

In the Supabase Dashboard, open:

**Authentication -> General Configuration**

Enable:

**Allow anonymous sign-ins**

No email provider or redirect URL is required for this version.

## 3. Local configuration

Your `.secrets` now only needs:

```text
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_KEY
VITE_SUPABASE_STATE_ID=household
```

`VITE_ALLOWED_EMAILS` is no longer used.

Then:

```bash
npm install
npm run dev
```

On first launch, enter the household access code generated by `setup.sql`.

## 4. GitHub Pages secrets

In:

**GitHub repository -> Settings -> Secrets and variables -> Actions**

you only need:

- `SUPABASE_URL`
- `SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_STATE_ID`

`ALLOWED_EMAILS` can be deleted.

Push normally. The GitHub Actions workflow builds the app without any email
configuration.

## 5. Using another phone/device

Open the GitHub Pages app on that device and enter the same household access
code once.

That device then receives the same Supabase-backed planner state.

Concurrent changes to different planner, meal, or shopping records are merged
automatically. If two devices edit the same information, both versions remain
available until someone chooses which overlap to keep. Offline changes are
stored in IndexedDB and retried after the browser reconnects.

## Important behavior

Anonymous Supabase sessions persist in browser storage. Normally, reopening the
app requires no code.

If a user clears the browser/site data, uses private browsing, or loses the
anonymous session, that browser cannot recover the old anonymous identity.
Simply enter the household code again; it will enroll a new anonymous user ID.

## Existing email-auth users

You do not need to delete old Supabase Auth users.

After installing this version, an existing logged-in Supabase user can also
enter the household code and become a member. New devices use anonymous auth.

## Security

The household code is never embedded in the GitHub Pages JavaScript bundle.
Only the Supabase publishable key is public.

The code is sent to a server-side Postgres RPC, which compares its hash and
adds `auth.uid()` to `meal_planner_members`. RLS then grants access only to
enrolled IDs.

Choose/protect the generated household code like a password. Anyone who obtains
it can enroll a new device.

Supabase recommends CAPTCHA/Turnstile for public applications using anonymous
sign-ins to reduce automated account creation abuse. For a tiny private
household app this implementation leaves CAPTCHA optional rather than adding
another setup dependency.
